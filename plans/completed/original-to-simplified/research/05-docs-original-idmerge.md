## Summary

Original ID Merge builds identity clusters out of three special identity events — `$identify`,
`$create_alias`, and `$merge` — rather than out of `$device_id`/`$user_id` properties on ordinary
events (which is how Simplified works). A cluster may contain at most **500** distinct IDs; once a
cluster is full, further IDs cannot be merged in and become "orphaned duplicates" (separate users).
Mixpanel picks the cluster's canonical `distinct_id` **programmatically** ("based on the most
optimal merging process") — it can be a device ID or a user ID, is **not user-configurable**, and
is the only ID usable in queries/exports (any ID in the cluster remains valid for ingestion).
Merging is retroactive (historical events re-resolve to the canonical ID; propagation takes up to
24h) and **irreversible**. Critically for this sprint: Simplified ID Merge projects **ignore**
`$identify`, `$create_alias`, and `$merge` events entirely, and Simplified does **not** support
multiple identified (user) IDs in one cluster — so a replay pipeline must translate original-system
identity verbs into `$device_id`/`$user_id` pairings and must decide what to do with clusters that
contain more than one user ID.

## Key Facts

- Three identity verbs, exact event names: `$identify`, `$create_alias`, `$merge`.
- `$identify` properties: `$identified_id` (required), `$anon_id` (required), `token` (required),
  `distinct_id` (optional — "inferred from $identified_id if not included").
- `$identify` only merges an `$anon_id` that is (a) **UUIDv4 format** ("anonymous ID format
  generated by Mixpanel and Segment") and (b) "not previously merged to another `$identified_id`".
- `$create_alias` properties: `distinct_id` (required), `alias` (required), `token` (required).
  "A new distinct_id [`alias`] to be merged with the original distinct_id."
- Alias rules: "Multiple alias ID can point to the same Distinct ID, aliases can be daisy-chained,
  but the same alias ID cannot point to multiple different Distinct IDs." / "Each alias can only
  map to one distinct_id." `$create_alias` is described as "a legacy function for projects not
  using ID Merge" (works in Original and pre-ID-merge Legacy; no functionality in Simplified).
- `$merge` properties: `$distinct_ids` — an array of **exactly 2** items (`minItems: 2`,
  `maxItems: 2`), plus `token`. "Allows you to merge any 2 identifiers together. Unlike the
  `$identify` events, there are no payload requirements" (i.e. no UUIDv4/not-previously-merged
  restrictions). Merges whole clusters: "allows merging of any 2 ID clusters as long as it does not
  exceed 500 total IDs."
- `$merge` is `/import`-only: "we will only accept `$merge` events that are sent via
  `https://api.mixpanel.com/import`, which is protected by the project api secret." It "cannot be
  triggered using any SDK methods."
- Cluster limit: "There is a limit of **500 IDs** that can be merged into a single ID cluster"
  (Original only; Simplified has "no limit on the number of `$device_id`s" per `$user_id`).
- Past the limit: "Once this threshold is reached, new Distinct IDs become **orphaned duplicates**"
  (migration doc). The merge fails; the extra ID behaves as a separate user.
- Canonical ID: "the canonical `distinct_id` is programmatically selected by Mixpanel, using one of
  the IDs inside of the identity cluster, based on the most optimal merging process … could be set
  to a `$device_id` or your chosen `user_id`. This is not user-configurable." "You can use any of
  the IDs in the cluster for ingestion, but only the canonical `distinct_id` can be used in queries
  and exports."
- Retroactivity: merging retroactively stitches event streams ("works even if a user has multiple
  anonymous sessions"). Activity feed reflects a merge "in real-time (less than 1 minute)"; other
  parts of the system "may take up to 24 hours" to propagate the mapping.
- "Merging identities is **irreversible**" — no unmerge.
- Simplified projects: "You should not send `$identify`, `$create_alias`, and `$merge` events since
  they will be **ignored** in Simplified ID Merge projects."
- Simplified "does not support multiple identified IDs (i.e. User IDs) per ID cluster" — Original
  supports this via `$merge` / `$create_alias`.
- Identity API version is per-project, set in Org Settings (or Project Settings for a data-less
  project), and "Once there are any data in your project, your Identity API version cannot be
  changed." Simplified is "the default for new organizations created from April 2024."

## Details

### The three identity verbs

#### 1. `$identify` — link an anonymous ID to a user ID

Fired by SDK `.identify(<user_id>)`, or ingested server-side. Payload:

```json
{
  "event": "$identify",
  "properties": {
    "$identified_id": "<user_id>",
    "$anon_id": "<device_id>",
    "token": "YOUR_PROJECT_TOKEN"
  }
}
```

Field semantics (from the API reference):

- `$identified_id` (string, required): "A distinct_id to merge with the $anon_id".
- `$anon_id` (string, required): "A distinct_id to merge with the $identified_id".
- `distinct_id` (string, optional): "inferred from $identified_id if not included".
- `token` (string, required): project token — this endpoint authenticates via token in the body,
  no HTTP auth header.

Validation constraints:

- `$anon_id` **must be UUIDv4** ("anonymous ID format generated by Mixpanel and Segment") — a
  non-UUIDv4 `$anon_id` will not be merged by `$identify` (use `$merge` instead).
- `$anon_id` must **not already be merged** to a different `$identified_id`. An anon ID gets one
  shot at `$identify`-based merging; subsequent `$identify` calls pairing it with a different user
  ID do not re-merge it. (This is the anti-account-sharing rule: one device ID can't be folded into
  two users' clusters via `$identify`.)
- The docs do **not** state what happens to a failing `$identify` event (silently ignored vs.
  ingested-as-event vs. error) — see Open Questions. With `strict=1` on `/track` the endpoint
  "will validate records and return error messages", but the specific error text for a failed merge
  is not documented.

Endpoint: `POST https://api.mixpanel.com/track#create-identity` (the `#create-identity` fragment is
docs-navigation only; the real endpoint is `/track`). `Content-Type:
application/x-www-form-urlencoded`, body `data={JSON}`. Optional `strict` (integer 0–1).
Responses: `200` with body `1` (valid) / `0` (invalid); `401` / `403` JSON errors. Reference notes
the alternative "import endpoint: `https://api.mixpanel.com/import/`" — i.e. `$identify` can also
be sent through `/import` like any event (which is what a replay pipeline would do).

"The `$identify` event payload is only useful for projects using the Original ID Merge system; it
has no functionality in other ID management systems."

#### 2. `$create_alias` — link two non-anonymous distinct IDs

"Used to link two non-anonymous Distinct IDs. It creates an 'alias' to another Distinct ID already
present in the identity cluster and adds the same alias ID into the same cluster." Payload:

```json
{
  "event": "$create_alias",
  "properties": {
    "distinct_id": "<existing_id>",
    "alias": "<new_id_to_add>",
    "token": "YOUR_PROJECT_TOKEN"
  }
}
```

- `properties.distinct_id`: "A distinct_id to be merged with the alias" (the ID already in the
  cluster).
- `properties.alias`: "A new distinct_id to be merged with the original distinct_id" (the ID being
  added).

Chaining/multi-mapping rules, verbatim:

- "Multiple alias ID can point to the same Distinct ID" — fan-in is fine.
- "aliases can be daisy-chained" — alias B→A, then C→B is fine; all land in one cluster.
- "the same alias ID cannot point to multiple different Distinct IDs" / "Each alias can only map to
  one distinct_id" — fan-out is rejected. Once `alias: X` has been pointed at one distinct_id,
  another `$create_alias` with `alias: X` and a different `distinct_id` will not merge.

Endpoint: `POST https://{region}.mixpanel.com/track`, region ∈ `api` (US default), `api-eu`,
`api-in`. Form-encoded `data={JSON}`, token-in-body auth, `200` → `1`/`0`, `401`, `403`.

Positioning: "This is a legacy function for projects not using ID Merge" — it exists in Original
ID Merge for backwards compatibility with the pre-ID-merge `alias()` flow, and is "only useful for
projects using the Original ID Merge system and the Legacy ID Management System; it has no
functionality in the Simplified ID Merge system."

#### 3. `$merge` — merge any two IDs / clusters

```json
[
  {
    "event": "$merge",
    "properties": {
      "$distinct_ids": ["id1", "id2"],
      "token": "your_token"
    }
  }
]
```

- `$distinct_ids`: array of **exactly 2** strings (`minItems: 2`, `maxItems: 2`).
- "The `$merge` event allows you to merge any 2 identifiers together. Unlike the `$identify`
  events, there are no payload requirements." — no UUIDv4 restriction, no
  not-previously-merged restriction. This is the escape hatch for anon↔anon merges, merging two
  identified users, non-UUID anonymous formats, and repairing clusters.
- Merges are cluster-wise: sending `$merge` on two IDs unions their entire clusters. "It is
  possible using the $merge API event, which allows merging of any 2 ID clusters as long as it does
  not exceed 500 total IDs." / "As long as the merging of 2 IDs does not lead to an ID cluster that
  exceeds 500 IDs, it will be successful."
- Transport restriction: "This event cannot be triggered using any SDK methods; it can only be
  processed when sent via the /import API directly." Rationale, verbatim: "`$merge` is a very
  powerful tool, so we will only accept `$merge` events that are sent via
  `https://api.mixpanel.com/import`, which is protected by the project api secret."

Endpoint: `POST https://{region}.mixpanel.com/import`, region ∈ `api`, `api-eu`, `api-in`. Auth:
HTTP Basic with Service Account, HTTP Basic with Project Secret, or OAuth Bearer token. Query
params: `strict=1` (recommended; per-event validation errors) and `project_id` (needed with
service-account auth). Responses: `200` `{"code": 200, "status": "OK", "num_records_imported": N}`;
`400` validation failure with a detailed error array (index, field, message); `401` `"Invalid
service account credentials"`.

"Merging identities is irreversible."

### Cluster semantics

- An identity cluster is the set of distinct IDs known to belong to one user. Events ingested under
  **any** ID in the cluster resolve to the same user.
- Hard cap: **500 IDs per cluster** (Original only). A merge that would push a cluster past 500
  fails, and "new Distinct IDs become orphaned duplicates" — i.e. events under the unmergeable ID
  show up as a separate user. Exact error/status emitted at ingestion time is not documented.
- Canonical `distinct_id`: chosen by Mixpanel from among the cluster's IDs "based on the most
  optimal merging process"; may be a `$device_id` or a user ID; **not configurable**; the only ID
  valid in queries and raw exports (ingestion accepts any cluster member). Implication for this
  sprint: the `distinct_id` on events exported from an original project is the canonical cluster
  ID, which may be an opaque device UUID rather than the "real" user ID.
- Retroactive merging: after a merge, previously ingested events under any cluster member resolve
  to the canonical ID — "works even if a user has multiple anonymous sessions (eg: on desktop and
  mobile)". Propagation timing: Activity feed "in real-time (less than 1 minute)"; everything else
  "may take up to 24 hours".

### Worked lifecycle examples (from the Original docs page)

1. **New user signup**: device has anonymous `$device_id` D1; anonymous events track with
   `distinct_id = D1`. On signup, `.identify(U1)` fires `$identify {$identified_id: U1, $anon_id:
   D1}` → cluster `[D1, U1]`. Pre-identify events retroactively resolve to the canonical ID.
2. **Returning user, new device**: new device generates D2, user logs in, `.identify(U1)` merges
   D2 into the existing cluster → `[D1, U1, D2]`.
3. **Multiple users, one device**: user 1 is `[D1, U1]`; on logout `.reset()` clears local storage
   (containing `$user_id` and `$device_id`) and generates a fresh D2; user 2's `.identify(U2)`
   creates a separate cluster `[D2, U2]`. Without `.reset()`, D1 could not be `$identify`-merged
   into U2's cluster anyway (already merged to U1) — but events would keep flowing into U1's
   cluster.

Warnings, verbatim: "Call `.reset()` frequently can result to reaching the cluster limit within a
short time." / "Best practice would be to only call reset() if there is definite intent to change
user on same device." / "Track the unique identifier as super property and user property to assist
troubleshooting."

### User profiles

"User Profiles are set directly on $distinct_ids. We recommend waiting until after a user is
identified before setting user profile properties." / "Avoid creating profiles for anonymous
users." (Profiles do not automatically consolidate across a cluster the way events do — set them
on the identified/canonical ID.)

### Third parties / anonymous ID formats

- UUIDv4 is called out as the "anonymous ID format generated by Mixpanel and Segment" — Segment
  `anonymousId`s satisfy `$identify`'s format rule.
- CDPs (Segment, Rudderstack): "Call .identify() when user signs up or logs in … Call .reset() when
  user logs out."
- Attribution SDKs (AppsFlyer, Adjust, Branch) should "set $device_id to whichever ID they use for
  attribution."
- Anonymous IDs in any other format (e.g. Amplitude device IDs that aren't UUIDv4, custom session
  IDs) can only be merged via `$merge`.

### Determining a project's ID management system

- Org level: Organization Settings; project level: Project Settings (changeable only while the
  project has no data). "Once there are any data in your project, your Identity API version cannot
  be changed." "You cannot switch between the two APIs if your project already contains data in
  it."
- "Simplified ID Merge API is the default for new organizations created from April 2024."
- Pre-ID-merge ("Legacy") projects exist too; their alias-based docs live at
  https://github.com/mixpanel/docs-legacy/blob/main/legacy/aliases.md.
- Full comparison, verbatim — Simplified: "Distinct IDs are determined using `$user_id`/`$device_id`
  in events"; "The `$user_id` is always set as the distinct_id for the user"; "There is no limit on
  the number of `$device_id`s that can be merged into a single `$user_id`"; "Any IDs in the cluster
  can be used for ingestion." Original: "Distinct IDs are determined using the `$identify`,
  `$merge`, and `$create_alias` events"; "The distinct_id is automatically determined by Mixpanel
  using one of the IDs in the cluster"; "There is a limit of 500 IDs that can be merged into a
  single ID cluster"; "Any IDs in the cluster can be used for ingestion."

### Hot-shard limits (separate from cluster limits — don't conflate)

From `/docs/debugging/distinct-id-limits`; these apply per event **date**, in any ID system:

- "200K events per `distinct_id` per event date" (user analytics); "1M events per `group
  identifier` per event date" (group analytics).
- Past the threshold, subsequent same-day events are **transformed, not dropped**: event name →
  `$hotshard_events` (original kept in `mp_original_event_name`); `distinct_id` → `""` (original
  kept in `mp_original_distinct_id`).
- Org owners get an email plus a monthly report; remediation = fix the implementation, optionally
  re-import corrected history.
- Relevance to replay: a naive replay that rewrites many users onto one distinct_id (or `""`) can
  trip this; also, exported data may already contain `$hotshard_events` rows whose real identity is
  in `mp_original_distinct_id` / `mp_original_event_name`.

### Migration-relevant statements (original-side; simplified mechanics are another slice)

- "You should not send `$identify`, `$create_alias`, and `$merge` events since they will be ignored
  in Simplified ID Merge projects." → replay must **translate**, not forward, identity verbs.
- Historical events that already carry `$device_id` and `$user_id` properties (SDK-tracked) "can be
  directly imported into the new Simplified ID Merge project as they include reserved properties
  required for identity merging."
- Simplified "does not support multiple identified IDs (i.e. User IDs) per ID cluster," while
  Original does (via `$merge`/`$create_alias`). Original clusters with 2+ user IDs cannot be
  represented 1:1 in Simplified — the pipeline needs a policy (pick one user ID as `$user_id`,
  map the rest via a property, or split).

## Gotchas / Limits

- **500 IDs per cluster** (Original). Exceeding → merge fails, new IDs are "orphaned duplicates."
  No documented error message/status for the failed merge at ingest time.
- **`$identify` is picky**: `$anon_id` must be UUIDv4 AND never previously merged to another
  `$identified_id`. Anything else needs `$merge`.
- **`$merge` takes exactly 2 IDs** per event (`minItems: 2, maxItems: 2`) and is `/import`-only
  (secret / service account / OAuth — not token auth).
- **Alias fan-out is illegal**: one alias → one distinct_id, forever. Fan-in and daisy-chaining are
  legal.
- **Canonical ID is Mixpanel's choice**, may be a device UUID, not configurable — exported
  `distinct_id` values from an original project reflect this choice, not necessarily the user ID.
- **Merging is irreversible.**
- **Retroactive propagation lag**: up to 24 hours outside the Activity feed. An export taken <24h
  after late merges may show stale identity resolution.
- **Identity verbs are silently ignored by Simplified projects** — replaying them as-is loses all
  identity information without any ingestion error.
- **Simplified allows only one `$user_id` per cluster** — multi-user-ID original clusters are the
  hard translation case.
- **Hot-shard rewrite** (200K events/distinct_id/day → `$hotshard_events`, `distinct_id: ""`) is a
  separate mechanism that both source exports and replay ingestion can encounter.
- Docs never specify the failure mode of an invalid `$identify`/`$create_alias` at ingest (silent
  no-op vs `strict` error) — must be determined empirically.

## Open Questions

1. **Failed-merge semantics**: exact behavior when `$identify` violates its rules ($anon_id not
   UUIDv4, or already merged) or when a `$merge` would exceed 500 IDs — silently accepted-as-event?
   Rejected under `strict=1` with a specific error code/message? Needs an empirical test against a
   throwaway original-ID-merge project (org must predate April 2024 defaults or have the toggle).
2. **Export representation**: do raw exports from an original project include a property like
   `$distinct_id_before_identity` (or `$mp_distinct_id_before_identity`) carrying the pre-merge
   distinct_id? None of the fetched pages confirm the property name — verify against the raw export
   API docs / a real export. This determines whether the replay pipeline can recover the original
   per-event ID or must reconstruct clusters solely from exported `$identify`/`$merge`/
   `$create_alias` events.
3. **Do identity events appear in raw exports at all** ($identify/$create_alias/$merge rows), and
   with what properties? Not documented; needs verification against a real export from
   project 3996669 (the repo's event-export test project).
4. **Anon↔anon via `$identify`**: docs imply `$identified_id` is a "non-anonymous" ID but never
   forbid a UUIDv4 there; `$merge` definitely handles anon↔anon. Confirm whether `$identify` with
   two UUIDv4s merges.
5. **Is there an API to read a project's identity clusters** (canonical ID → members)? Not
   mentioned in any fetched page; if none exists, cluster reconstruction must be done client-side
   from replayed identity events.
6. **Which ID does Mixpanel actually pick as canonical** ("most optimal merging process" is
   opaque) — is it deterministic (e.g., first ID seen)? Matters only if the pipeline tries to
   predict source-side canonical IDs instead of reading them from the export.
